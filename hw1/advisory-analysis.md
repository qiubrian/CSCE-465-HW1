My security report or advisory report will be over GHSA-3mq7-q27j-mq7q, a vulnerability where openclaw's exec approval system remembered reusable command approvals outside the working directory and into other directories without reapproval. This was patched in the openclaw system version 2026.8.1 by binding reusable approvals to the directory they were approved on and the command it was approved for.

This vulnerability was a problem because when openclaw would ask to execute a command that, in the scope of the context it was being executed in, appeared to be harmless and aligned with the work being done in that directory. For example, openclaw could ask to execute the command 'rm data.txt', which might be harmless and intended for that scope. However, if an attacker was able to use openclaw to run the same command 'rm data.txt' from a different working directory, that command would be executed without asking for authorization, even though the command was run in a different directory. This means 'rm data.txt' could delete a different data.txt file in another working directory without user authorization for that directory. This problem was caused by an oversight to how reuseable exec command approvals were saved, openclaw originally just "remembered" that the command was approved, but it didnt take into account that the scope of the command was important too. Because command context/location of execution is equally as important, it should have been treated as a part or limit of the approval.

For an attacker to exploit this vulnerability, the attacker would need the user to give reusable approval for an exec command. The attacker would then need a way to make openclaw run that exec command in a different working directory. Because the reusable approval was bound to the command it was approved for, the attacker could only use that reusable approval for other working directories, potentially affecting sensitive files or resources.

The vulnerability was fixed by changing how the reusable exec command approvals were stored and connected. The patch made it so that reusable exec command approvals are bound to the exact command they were approved for and the exact working directory it was approved in. This means if an attacker were to be able to gain access and run the previously saved approved command in a new directory, openclaw would ask the user for approval again, as its not in the same directory anymore. 

The impact of this vulnerability could be serious, but also heavily dependant on which command was given reusable approval. If it was approved for a general command, like modification or reading files, it could be used to expose or break sensitive files or code. Permissions to affect a git repository are also a possible impact, as if a user had previously given reusable approval to a Git command that modified or deleted repository contents, that same reusable approval for a command could be used to modify or delete other repositories as well without user approval.

A regression test could be done by creating two different directories that both contain a file named data.txt. In the first directory, the user could give cat data.txt a reusable approval. OpenClaw could then be asked to run the exact same cat data.txt command from the second directory. On a patched version, OpenClaw should not reuse the first approval and should require another approval for the second directory.

Prompt injection isnt required, but is helpful for this vulnerability. Using prompt injection, an attacker could sneak a hidden command to execute a known command that was given reusable approval on a different working directory. This helps the attacker send the instructions to expose the vulnerability and take advantage of it, but isnt required for the vulnerability itself.
